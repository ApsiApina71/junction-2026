# Owl contract: data model and API

The shared JSON shapes and endpoints of `apps/owl-api`. The glasses app (`apps/owl-glasses`) and Owl Studio build against this, first on the mock data in [`apps/owl-api/fixtures/`](../../apps/owl-api/fixtures/), then on the real engine. Same shapes in both.

- **Ticket:** [JUN-27](https://linear.app/junction-2026-bossit/issue/JUN-27). The API is [JUN-28](https://linear.app/junction-2026-bossit/issue/JUN-28).
- **Spec:** [Owl Boarding](onboarding-owl.md)
- **Owner:** the owl-api session. Ask for changes; do not edit this file from another app's work.

## Basics

- Base URL `http://<mac ip>:8000` on the venue network, plus an `https://` tunnel URL for video (see [Media](#media)).
- JSON, UTF-8, `snake_case` keys. Missing optional fields are `null`, never left out.
- **Auth:** when the server sets `API_TOKEN`, every endpoint except `/health` and `/media/*` needs the header `X-Api-Token: <token>`. Without it the API answers `401`.
- **Errors:** `{"detail": "<one sentence for a human>"}` with the status code:

| Code | When | What the glasses app does |
|---|---|---|
| 400 / 415 / 413 | Bad upload (not an image, wrong type, too big) | Bug; log it |
| 401 | Wrong or missing token | "Ask your supervisor" screen |
| 404 | Unknown process, step, help or record id | Reload the process list |
| 422 | Missing or invalid field | Bug; log it |
| 429 | Model rate limited | Retry after 2 s |
| 503 "The model is not set up on this server yet." | No API key on the server yet (JUN-68) | Same as below |
| 500, 502, 503, no answer | Server bug, model or network error | "Owl can't see right now" and keep going without the check. A step finished this way is **not checked**: never show it as verified (JUN-57) |

- **Languages** are BCP 47 tags (`en`, `fi`, `uk`, `ar`). `say` and `text` fields come in the employee's language. See [Languages](#languages).

## Display limits (from the DAT docs)

Meta Ray-Ban Display renders at **600×600**. Owl keeps text short so a step fits on one screen.

| Field | Limit |
|---|---|
| `Step.title` | ≤ 32 characters |
| `Step.instruction`, `CheckResult.text`, `Answer.text` | ≤ 140 characters |
| Every `say` | ≤ 25 words, no markdown or emoji |
| Images (`*_image_url`) | JPEG, longest side ≤ 600 px |
| Clips (`clip_url`) | MP4 (H.264), ≤ 400 px per side and ≤ 70 000 pixels in total (for example 352×198 or 264×264), `https` only, one at a time |

## Shapes

### Employee

```json
{
  "id": "emp-sami",
  "name": "Sami",
  "language": "en",
  "role": "Warehouse picker",
  "company": "Kide Logistics",
  "welcome": "Welcome to Kide, Sami! Today you learn to pick and pack an order. I'm Owl. I'll show you each step.",
  "process_ids": ["proc-pick-pack"],
  "glasses_id": "glasses-1"
}
```

- `company`: the company of the worker's first task; without a task, the company this owl-api runs for (`OWL_COMPANY`, by default the demo worker's). One company per server: multi-company admin is out of scope.
- `welcome` is the personal welcome shown and spoken on the first start (JUN-41). Owl writes it from the name, the company and the first task, in the employee's language, and rewrites it when one of those changes. A welcome written by hand in Owl Studio stays as written.
- `access` (JUN-81): `{"audio_first": bool, "display_first": bool, "easy_language": bool}`, all `false` by default; Studio sets it. **audio_first** (low vision, or eyes busy): the glasses speak everything on the display too. **display_first** (Deaf or hard of hearing, or a loud workplace): every spoken line is also a caption, and a warning stays until a pinch. **easy_language**: the server's own sentences (checks, Ask) come in easy language when `/check` and `/ask` carry the worker's `employee_id`; a process can be stored in easy language with a `-x-easy` language tag. The fixtures have one worker per profile: Amina (easy language, `glasses-3`), Leo (display first, `glasses-4`) and Ville (audio first, Finnish, `glasses-5`).
- `glasses_id` is the pair of glasses the employee wears, or `null`. The employer names the pairs (`glasses-1`; letters, digits, `-` and `_`). A pair has one worker at a time: assigning it to someone takes it from whoever had it.

### Process

```json
{
  "id": "proc-pick-pack",
  "title": "Pick and pack an order",
  "summary": "Take a box, pick the items on the order, check them, pack and seal.",
  "company": "Kide Logistics",
  "language": "en",
  "status": "published",
  "source": "record",
  "expert": "Laura",
  "steps": [Step, ...]
}
```

- `status`: `draft` (just recorded, only in Owl Studio) or `published` (shown on the glasses).
- `source`: `record` (an expert recorded it) or `docs` (written from the documents).

### Step

```json
{
  "id": "step-2",
  "index": 2,
  "title": "Pick the items",
  "instruction": "Pick every item on the order from the shelf into the box.",
  "say": "Pick the three items on the order into the box.",
  "reference_image_url": "https://owl.example/media/proc-pick-pack/step-2.jpg",
  "clip_url": "https://owl.example/media/proc-pick-pack/step-2.mp4",
  "check": {
    "kind": "order",
    "criteria": ["Every order line is in the box", "No extra items"],
    "order_lines": [{"sku": "OAT-1L", "name": "Oat drink 1 l", "qty": 2}]
  },
  "source": {"doc": "Laura's recording", "quote": "Always check the litre size, the 0.5 l and 1 l cartons look the same."},
  "reviewed": true
}
```

- `index` starts at 1.
- `say` is what the glasses speak when the step opens. `instruction` is the text on the display.
- `reference_image_url`: the expert's photo of the finished step, or `null`.
- `clip_url`: a 5–10 s clip of the expert doing the step ("Watch how"), or `null`.
- `check.kind`:
  - `visual`: the camera view is checked against each of the `criteria`. The reference image is shown to the vision model as context and on the display, but it never decides on its own: a step passes only when every criterion was seen and met. A visual step without criteria can never pass.
  - `order`: the products and quantities seen are compared with `order_lines`.
  - `none`: no check. The worker confirms the step with a pinch.
- `check.order_lines` is set only for `order` checks.
- `reviewed` (default `true`): `false` on a step that Owl wrote from a recording or a document and that no person has checked yet. Owl Studio sets it to `true` when the reviewer has read the step against the narration. `PUT /processes/{id}` answers `422` when the body is `published` and a step is not reviewed; saving a draft is always allowed.
- `source` is where the step comes from, or `null`: the document quote for a process written from documents, the expert's whole narration for a recorded one.
- `rule`: the company rule from the handbooks that backs this step (`{doc, section, quote}`, quoted word for word), or `null`. Owl finds it locally for recorded steps (JUN-70). Show it as "Company rule".
- `checkpoint`: where the step happens, `{"zone_id": "zone-c", "label": "Aisle C · Shelf 12", "photo_urls": []}` (label ≤ 40 characters, up to 8 extra photos of the place), or `null`. During training the step is locked until Owl recognises the place in the camera picture (JUN-97, see Location). A translation has the same checkpoints as the original.

### CheckResult

Answer to one camera frame during a step.

```json
{
  "status": "warning",
  "problem": "wrong_item",
  "text": "Wrong size: 0.5 l. The order says 1 l.",
  "say": "Wrong item: 0.5 l, the order says 1 l.",
  "hint": null,
  "lines": [
    {"name": "Oat drink 1 l", "expected": 2, "seen": 1, "status": "wrong_item", "note": "1 × Oat drink 0.5 l"},
    {"name": "Coffee 500 g", "expected": 1, "seen": 1, "status": "ok", "note": null},
    {"name": "Rye crispbread", "expected": 1, "seen": 1, "status": "ok", "note": null}
  ],
  "confidence": 0.91,
  "decided_by": "jev",
  "step_done": false
}
```

- `status`:
  - `ok`: the step looks right. If the request had `final: true`, `step_done` is `true`.
  - `warning`: a problem was seen in two frames in a row. Show `text` and speak `say`. `say` is set only on the frame where the warning is confirmed or changes, and on every Done pinch; while the same problem stays, later frames repeat `text` with `say: null`.
  - `checking`: a problem was seen once and waits for the next frame. `say` is `null`, so stay quiet.
  - `unsure`: Owl cannot tell (blurry, too far, hand in the way). `hint` says what to do ("Move closer to the box"). Speak it only on a final check.
- `problem`: `wrong_item | missing | too_many | not_matching | null`. `not_matching` is for visual steps.
- `lines`: one row per order line for `order` checks. `null` for `visual` and `none`.
  - `lines[].status`: `ok | wrong_item | missing | too_many`.
  - `lines[].note`: what was seen instead, or `null`.
- `confidence`: Jev's reported probability for its answer (0–1), or `null` when the rules decided alone. It is not a calibrated chance that the step is right: **never show it as a percentage**.
- `decided_by`: `jev` (Jev agreed with the rules above the server's threshold), `rules` (the deterministic compare decided alone, for example without a Jev key) or `demo` (demo mode: the camera observation is scripted, see below).
- `next_check_ms` (JUN-82): when the glasses should look again: 800 while a problem is being confirmed, 1500 after a warning or an unsure frame, 3000 while the step looks right, and `null` when the step is done or has no check (wait for the next step or a pinch). A run gets at most `MAX_CHECKS_PER_MINUTE` (40) model calls; above that the answer is `checking` without a model call.
- `step_done`: `true` only when `final` was sent and the step is right. **A step is never done while something is wrong.**

**What a passed check means.** Vision describes one frame; the rules decide from that description. A product vision did not map to an order line counts as something extra in the box, and a criterion that was not answered is not passed (`unsure`). Jev, when on, is a second opinion on the decision from the same description: it cannot catch an item vision missed or misread. The "two frames in a row" rule is consistency over time from the same model, not an independent confirmation. So a passed check covers only what was visible in the frame and reviewed against the step, and the apps say no more than that ("Owl checked the box", not "the order is correct").

### Answer

```json
{
  "found": true,
  "text": "Mark the line as missing on the order and tell the shift lead. Never swap in another product.",
  "say": "Mark it missing and tell the shift lead. Don't swap in another product.",
  "language": "en",
  "sources": [{"doc": "Warehouse handbook", "section": "Out of stock", "quote": "If an item is out of stock, mark the line as missing and tell the shift lead."}]
}
```

`found: false` means the answer is not in the company's instructions. `text` then says so ("That's not in our instructions. Ask your shift lead."), and `sources` is `[]`.

### Doc

```json
{"id": "doc-handbook", "title": "Warehouse handbook", "filename": "warehouse-handbook.md", "chars": 2400, "uploaded_at": "2026-11-14T09:00:00+02:00"}
```

### HelpSession

```json
{
  "id": "help-1",
  "status": "waiting",
  "employee_id": "emp-sami",
  "process_id": "proc-pick-pack",
  "step_id": "step-2",
  "latest_frame_url": "https://owl.example/media/help/help-1-Zk3vTq8mXw2LrN5d/latest.jpg?t=9f2c1a7b",
  "frame_at": "2026-11-14T10:12:18+02:00",
  "updated_at": "2026-11-14T10:12:20+02:00",
  "messages": [
    {"id": 1, "from": "worker", "text": "Which oat drink is it?", "at": "2026-11-14T10:12:00+02:00", "image_url": null},
    {"id": 2, "from": "expert", "text": "The blue carton, top shelf.", "at": "2026-11-14T10:12:20+02:00", "image_url": "https://owl.example/media/help/help-1-Zk3vTq8mXw2LrN5d/mark-2.jpg"}
  ]
}
```

- `status`: `waiting` (no expert yet), `connected` (an expert has answered), `ringing` (calling the manager on shift), `accepted` (the manager answered on their glasses), `ended`. See "Help from the shift manager" (JUN-100).
- `routed`: `studio` (the console) or `manager`. `assignee` and `assignee_name`: the manager the call rings for, or `null`; after a fall back to Studio `assignee` is `null` and `assignee_name` still says who did not answer. `rang_at`: when it started ringing. `fallback`: `null`, `no_answer` (30 s without an answer), `later` (the manager said Later) or `no_manager` (no one on shift).
- The glasses speak every `expert` and `manager` message once. `id` grows, so the app remembers the last one it spoke.
- `frame_at`: when the latest frame arrived. `updated_at` also moves when someone speaks, so the console uses `frame_at` to tell a live view from a stale one.
- `messages[].image_url`: the worker's own view with a ring where the expert pointed, or `null`. The glasses show it with the expert's words.
- When the session ends, its frames are deleted, and `latest_frame_url` and every `image_url` become `null`.

### Recording

```json
{
  "id": "rec-1",
  "title": "Pick and pack an order",
  "expert": "Laura",
  "status": "recording",
  "steps": [
    {"index": 1, "narration": "First take a medium box...", "photo_url": "https://.../rec-1-Qm4xT7vLp2Zs/1.jpg", "clip_url": "https://.../rec-1-Qm4xT7vLp2Zs/1.mp4", "key": "6F1C…"}
  ],
  "process_id": null,
  "dropped": [],
  "media_dir": "rec-1-Qm4xT7vLp2Zs"
}
```

- `status`: `recording`, `processing` (the AI is writing the steps), `done` (`process_id` is set), `failed`.
- `key` is the glasses' own name for a step upload (or `null`), and `dropped` lists the keys of uploads the expert gave up; see `DELETE /record/{id}/steps/{key}`.
- `media_dir` is the folder of the recording's photos and clips under `/media`. `/media/*` is served without a token, because the glasses' display loads pictures and clips by address, so the folder name ends in random letters like a Help session's. An address is as private as the link itself: whoever has it can open it.

### `POST /employees` and `PUT /employees/{id}`

```json
{"name": "Aino", "language": "fi", "role": "Packer", "process_ids": ["proc-pick-pack"], "glasses_id": "glasses-1", "welcome": null}
```

- `POST` needs `name` (1–60 characters) and `language`. `role` defaults to `""`, `process_ids` to `[]`, `glasses_id` to `null`.
- The server makes the `id` from the name (`emp-aino`, then `emp-aino-2`) and takes `company` from the employees and processes it already has.
- `welcome` empty or `null`: Owl writes it. English and Finnish have their own wording; other languages get the English one until someone writes theirs by hand.
- `PUT` changes only the fields that are sent. `"glasses_id": null` takes the glasses away, and `"welcome": ""` hands the welcome back to Owl.
- An unknown id in `process_ids` is a `422`. `PUT` on an unknown employee is a `404`.

### `GET /glasses/{glasses_id}/employee`

The glasses app asks this on "Hey Meta, start Owl" to learn who wears this pair. `404` with `{"detail": "These glasses are not assigned to anyone yet."}` when no one does.

### `PUT /processes/{id}`

- The server numbers `Step.index` 1, 2, 3… from the order of `steps` and keeps every step `id`, so Owl Studio reorders and deletes steps by sending the array as it should be. Two steps with the same `id` are a `422`.
- Without `?language=` the body replaces the process itself. Its `language` can be corrected this way too (a recording's language is a guess). When its words or its language change (titles, instructions, `say`, checks, sources, the steps or their order), stored translations are dropped, because they would say what the process used to say. Publishing alone keeps them.
- With `?language=sv` the body is stored as that language's translation, and the original does not change. It must keep the original's step ids in the same order (`422` otherwise). Its `status` is ignored: publishing happens on the original.

### `DELETE /docs/{id}`

Ask stops using the document at once and the uploaded file is deleted. `404` for an unknown id. The handbook that ships in `fixtures/docs/` is only forgotten until the server restarts.

### `POST /check`

Multipart form:

| Field | Type | Notes |
|---|---|---|
| `image` | file, `image/jpeg` or `image/png`, ≤ 6 MB | A camera **stream** frame, not a photo capture: Meta's known issue says capture holds back display updates on Display glasses. |
| `clip` | file, `video/mp4` or `.mov`, ≤ 18 MB | **Instead of `image`**, when the phone cannot decode the stream itself: about 1 s of the hvc1 (or H.264) stream, starting at a key frame. The server uses its last frame. Send exactly one of `image` and `clip` (both or neither: `422`; an unreadable clip: `400`). |
| `process_id` | text | |
| `step_id` | text | |
| `run_id` | text | A UUID the glasses app makes when the worker starts a process. The "two frames in a row" rule is kept per run and step. |
| `final` | text `true` / `false`, default `false` | `true` on the "Done" pinch. |
| `language` | text, optional | Defaults to the employee's language. |
| `employee_id` | text, optional but always sent by the glasses | The worker: their consent (JUN-80), their access profile (JUN-81) and their own learning progress (JUN-73). Without `camera_checks` consent the answer is `403 {"detail": "consent_required"}` and the frame is not read. |

Why `clip`: with the phone locked in a pocket the app runs in the background, and the DAT `raw` video codec stops delivering frames there; `hvc1` keeps delivering compressed frames ([VideoCodec](https://wearables.developer.meta.com/docs/reference/ios_swift/dat/1.0/mwdatcamera_videocodec)). The phone decodes them when it can and falls back to `clip` when iOS refuses background decoding.

Send one frame at a time and wait for the answer, about one frame every 1–2 s during an order step. While the server is busy with the same run, it answers `{"status": "checking", ...}` at once.

### `POST /ask`

```json
{"question": "What if an item is out of stock?", "employee_id": "emp-sami", "process_id": "proc-pick-pack", "step_id": "step-2", "language": "en"}
```

Only `question` is required. The question is the final transcription from the glasses' Speech capability.

When all documents together are larger than `ASK_MAX_CHARS`, only the best sections for the question go to the model, picked by a local BM25 index on this server (JUN-71). Source quotes are still checked against the whole documents.

A document titled `"<company>: ..."` belongs to that company: a worker of another company never gets answers from it (`Store.docs_for`). Documents without a known company name are for everyone.

### `POST /processes/{id}/translate`

"Hire anyone" (JUN-72): Owl writes the process in the worker's language and stores it, so `GET /processes?language=<lang>` returns it from then on. Everything but the words is kept: step ids and order, media, check kinds, SKUs and quantities. Order line names stay as printed on the order and the shelf labels. The same language as the process returns the process. It needs the model: in demo or mock mode it answers `503` "Translation needs the model", and a translation that does not keep the steps answers `502`.

### `POST /processes/from-docs`

The third knowledge level: a written instruction becomes a guided process in one click (JUN-70). With a model, Claude writes the steps (title, instruction, spoken sentence, check criteria) and quotes the document for each; a quote that is not in the document is dropped, never passed on. Without a model (demo or mock mode, or a model error), the document's first numbered list, or else its sections, become the steps. The result is a draft that a person reviews and publishes in Owl Studio. A document with no list and no sections answers `422`.

### Step recognition (JUN-34)

`POST /steps/recognize` answers which step the worker is doing, by comparing a short clip from the glasses with the expert's recorded clip of each step (cosine similarity of video embeddings; V-JEPA 2 when installed, otherwise a baseline descriptor):

```json
{"status": "ok", "step_id": "step-4", "similarities": {"step-1": 0.12, "step-2": 0.08, "step-4": 0.91, "step-5": 0.33}, "margin": 0.58, "backend": "vjepa2", "action": "Putting something into something"}
```

- With `run_id`, the last three clips of the run (within 10 s) are looked at together: a 2 s clip alone is a short look.
- `action`: what the clip shows in V-JEPA 2's own action words (its Something-Something v2 head), or `null` with the baseline. The stage timeline can show it.
- **Learning from confirmations:** when the worker confirms "Looks like step N" with a pinch, the glasses send `POST /steps/confirm`, and the run's last look is kept as one more example of that step: an embedding only, no video, not tied to the worker (at most 8 per step). More examples is what helps most (one example 65 %, three 80 % on real clips).

- `status: "unsure"` and `step_id: null` when the best step does not beat the second by `JEPA_MIN_MARGIN`, or when no step has an expert clip.
- The glasses show "Looks like step N" and move on only after a confirming pinch, never by themselves. Steps without an expert clip are not candidates.
- In demo mode (`OWL_DEMO=1`) the mock camera shows the same picture in every step, so the answer is scripted: the first step not yet done in the worker's current run, with `backend: "demo"`. With `OWL_DEMO_LIVE` listing `recognize` (real glasses), the model answers instead.
- Same consent rule as `/check` (`403 consent_required`). The clip is not stored. It guides; it never scores how well someone worked.

### Stage view (JUN-79)

Only the wearer sees the display, so `GET /stage` shows the audience the glasses screen, the camera view and a timeline of Owl's decisions (each check with its status and `decided_by`, each Ask with its source, each spoken line). The glasses send `StageUpdate` `{"glasses_id", "employee_id", "language", "screen": {"kind", "title", "text"}, "said", "step": {"process_id", "step_id", "index", "total"}}` on every screen change and spoken line, and a frame at most once a second, only while "Stage mirroring" is on in the phone settings (off by default). owl-api adds its own check decisions and answers to the timeline for the worker's glasses. The page takes `?token=` because a browser's EventSource cannot send headers. Nothing from the stage is stored.

### Consent and data practices (JUN-80)

`Consent`: `{"camera_checks": bool, "recording": bool, "location": bool, "at": "<time>" | null}`. `location` (JUN-97): during training, Owl recognises from the camera picture which place the worker has reached. The picture is not stored. The glasses ask on the first start, on the display and in the worker's language, and can ask again any time. Without `camera_checks`, Owl still guides but does not check (`/check` answers `403`). `recording` is the expert's agreement that Record keeps their clips.

| Data | Kept |
|---|---|
| Check frames | Never stored: read, described and dropped. |
| Help frames | In memory and on disk only while the help session is open; deleted when it ends. The same for a call to the shift manager (JUN-100): the manager's glasses only show the newest frame, nothing is recorded. |
| Recorded photos and clips | Faces blurred before storing; kept until the process is deleted in Studio. |
| Learning progress | Per worker, for their own glasses; erased with `DELETE /employees/{id}/progress`. Studio sees `/stats`, and per worker only the end-of-training result and its counts (JUN-96), after the worker has seen it. |
| Location (JUN-97) | Only during training and with `location` consent: the current area and today's areas, in memory only. Never on disk, gone on restart, dropped when training ends or consent is taken back. |
| Customer service transcript (JUN-98) | Never stored: used for one `/assist` answer and dropped. Not on disk, not in the logs, not on the stage view. |
| Consent | What was agreed and when. |
| Anything to Meta | Nothing: DAT analytics and crash reporting are opted out in the glasses app. |

### Learning progress (JUN-73)

Owl is a learning aid, not monitoring: the EU AI Act treats AI that monitors workers as high-risk. So the worker sees their own progress on their glasses, and the company sees only anonymous totals. **Owl Studio never shows one person's results**, except the end-of-training result below (JUN-96).

`GET /employees/{id}/progress` (the worker's own glasses only):

```json
{
  "employee_id": "emp-sami",
  "tasks_done": 2,
  "steps_done": 10,
  "problems_caught": 1,
  "problems_fixed": 1,
  "runs": [{"run_id": "…", "process_id": "proc-pick-pack", "title": "Pick and pack an order", "started_at": "…", "finished_at": "…", "seconds": 240, "steps_done": 5, "problems_caught": 0, "problems_fixed": 0}],
  "faster_than_first": true
}
```

- A run starts with its first `/check` and is finished when the process's last step is done. `runs` is newest first.
- `problems_caught` counts each spoken warning once; `problems_fixed` counts a warned step that then came out ok.
- `faster_than_first`: the latest finished run of a task against the first finished run of the same task, or `null` when there is only one.

`GET /stats` (no names, no ids): `{"runs", "tasks_finished", "workers", "median_seconds_to_first_finished_task", "problems_caught", "problems_fixed"}`. Runs live in memory and reset when owl-api restarts.

### Training period and target level (JUN-96)

The company sets per role how long training lasts and the level to reach: which steps must be verified how many times **without help**. At the end Owl suggests "ready" or "more practice", the worker sees it on the glasses first, and a person confirms it in Studio. Owl gives evidence; a person decides.

- A step counts when Owl verified it (`step_done` from `/check`) in a run where the worker did not ask Owl (`/ask` with that `employee_id`, `process_id` and `step_id`) or call for help (`/help/frames`) during that step. Mistakes the worker fixed do not count against them. Only runs started on or after `starts` count.
- No camera images, location or timing go into the result: only the counts below.

`GET /training/plans` → `{"plans": [TrainingPlan]}`. `PUT /training/plans/{id}` (Studio) saves one, `DELETE /training/plans/{id}` removes it.

```json
{"id": "plan-warehouse-picker", "role": "Warehouse picker", "days": 5, "customer_service": false,
 "target": [{"process_id": "proc-pick-pack", "step_id": "step-4", "required": 3}]}
```

`PUT /employees/{id}/training` `{"starts": "2026-11-11", "plan_id": null}` puts a worker on a training period (Studio). `plan_id` null: the plan whose `role` matches the worker's role (422 when none does). `{"starts": null}` ends it.

`GET /employees/{id}/training` (the worker's glasses; 404 when there is no training period):

```json
{
  "employee_id": "emp-sami", "plan_id": "plan-warehouse-picker",
  "starts": "2026-11-11", "ends": "2026-11-15", "day": 5, "days": 5, "days_left": 0, "active": true, "customer_service": false,
  "target": [{"process_id": "proc-pick-pack", "step_id": "step-4", "title": "Pack heavy items first", "task": "Pick and pack an order",
              "required": 3, "done_without_help": 2, "met": false}],
  "practise": [{"process_id": "proc-pick-pack", "step_id": "step-4", "title": "Pack heavy items first"}],
  "suggestion": "more_practice",
  "seen_at": null,
  "confirmed": null
}
```

- `ends` is the last day, inclusive. `title` and `task` are in the worker's language. `done_without_help` stops at `required`.
- `suggestion`: `"ready"` when every row is met (any day); `"more_practice"` from the last day on when some row is not; otherwise `null`.
- `confirmed`: `null` or `{"result": "ready" | "more_practice", "by": "Laura", "at": "<time>", "note": null}`.

`POST /employees/{id}/training/seen`: the glasses showed the suggestion to the worker. Sets `seen_at` (only while there is a suggestion) and answers the same object.

`POST /employees/{id}/training/confirm` `{"result": "ready" | "more_practice", "by": "Laura", "note": null, "extend_days": 3}` (Studio) → the same object. `409` before there is a suggestion or before the worker has seen it. `more_practice` is not a fail: training goes on `extend_days` more days from today, `seen_at` resets, and the worker sees the next suggestion first again.

`GET /training` (Studio) → `{"trainees": [...]}`: the same object per worker in training, with `name` and `role`. Until `seen_at` is set, `suggestion` is `null` and `waiting_for_worker` is `true`.

"Forget me" (`DELETE /employees/{id}/progress`) also drops `seen_at` and `confirmed`: the evidence is gone.

Demo mode: Sami is on day 5 of 5 with four earlier runs (`fixtures/training.json`, days counted back from today). Steps 1, 2, 3 and 5 are at 3 of 3, step 4 at 2 of 3, so the suggestion is `more_practice: Pack heavy items first`. One more run without help makes it `ready`.

### Location during training (JUN-97)

GPS does not work indoors, and there are no markers or codes to put up. **Owl recognises the place in the camera picture.** A step with a `checkpoint` is locked during training; while it is locked, the glasses send a picture now and then, and the step opens when Owl has recognised its place twice in a row.

Rules the server enforces: only during the worker's training period (JUN-96) and only with `Consent.location`. Today's history only, in memory: never written to disk, and dropped when training ends or the consent is taken back. **The camera picture is never stored** and never leaves the server: it is turned into a row of numbers, compared with the places, and dropped. No location goes into the training result.

`POST /location/frame` (multipart): `image` (JPEG) or `clip` (as for `/check`), `employee_id`, `process_id`, `step_id` (the locked step the worker is going to). One picture about every `next_check_ms`. Answers a Location with three more fields:

```json
{
  "employee_id": "emp-sami", "tracking": true,
  "zone": {"id": "zone-c", "name": "Aisle C"}, "entered_at": "<time>",
  "history": [{"zone_id": "zone-a", "name": "Aisle A", "entered_at": "<time>", "left_at": "<time>"},
              {"zone_id": "zone-c", "name": "Aisle C", "entered_at": "<time>", "left_at": null}],
  "unlocked": [{"process_id": "proc-pick-pack", "step_id": "step-2"}],
  "match": {"zone_id": "zone-c", "process_id": "proc-pick-pack", "step_id": "step-2", "score": 0.91, "decided_by": "model"},
  "can_recognize": true,
  "next_check_ms": 2000
}
```

- `match`: this picture looked like the step's place, or `null`. `decided_by`: `"model"` (DINOv2), `"baseline"` (without the optional extra) or `"demo"`. `score` is a similarity, never shown as a percentage.
- The step is in `unlocked` once two pictures in a row, within 10 s, matched (`PLACE_LOOKS`, `PLACE_WINDOW_S`). Then `zone` is the checkpoint's zone too.
- `can_recognize: false`: the step has no picture of its place yet. The glasses keep showing "Go to", and the trainer or a Help call opens it.
- Errors: `403 consent_required`, `409 not_in_training`, `404` unknown worker or a step without a checkpoint.

**How a place is recognised** (`app/place.py`): the pictures of a step's place are its `reference_image_url` (the expert's photo from the recording) and `checkpoint.photo_urls` (added in Studio). Every other step photo of the worker's tasks is a place too, so there is always something else a picture could look like. A picture matches when the target place is the closest of all and its similarity is at least `PLACE_MIN_SIM` (0.65 for DINOv2). Backend: `PLACE_BACKEND=auto` uses Meta's DINOv2-small (`uv sync --extra jepa`), else a colour-layout baseline that tells rooms apart but not aisles. Measured on a stand-in (20 videos as 20 places, the expert's photo early in a video and the worker's look later, from another angle): DINOv2 picks the right place in 90 % of looks, the baseline in 83 %. Aisles that look alike are harder: add place photos from more angles, and measure on the real site.

`GET /employees/{id}/location` → the same Location without the three extra fields. Outside training or without consent: `tracking: false`, `zone: null` and empty lists.

`POST /employees/{id}/unlock` `{"process_id", "step_id", "by": "trainer" | "help"}` → Location. When Owl does not recognise the place (new shelves, bad light).

`POST /location` `{"employee_id", "zone"}` or `{"employee_id", "checkpoint": {"process_id", "step_id"}}`: the worker is there, from another source than the camera (later: BLE beacons). Same Location and errors.

**Locked steps (glasses):** a step is locked when `tracking` is true, the step has a `checkpoint`, and it is not in `unlocked`. The glasses show "Go to: <label>" with the step's picture and send pictures to `/location/frame` until it opens. An unlock is used up when `/check` answers `step_done` for that step, so the next run asks for the place again.

Studio: `GET /zones` → `{"zones": [{"id", "name", "kind": "aisle" | "packing" | "loading" | "other", "x", "y", "w", "h"}]}` (x, y, w, h are shares of the map, from the top left). `PUT /zones/{id}` saves one, `DELETE /zones/{id}` removes it. Checkpoints are set on steps with `PUT /processes/{id}` (`checkpoint: {"zone_id", "label", "photo_urls"}`). `POST /processes/{id}/steps/{step_id}/place-photos` (multipart `image`) adds a picture of the place, faces blurred first, at most 8. `GET /locations` → `{"trainees": [{"employee_id", "name", "zone", "entered_at"}]}`: the live map, only workers in training who agreed.

Demo: Kide Logistics has Aisles A–C, Packing and Loading. Pick and pack step 2 is at "Aisle C · Shelf 12" (zone-c), step 4 at "Packing station" (zone-pack). In demo mode the camera's eyes are scripted: the second picture of a locked step opens it (`decided_by: "demo"`).

### Customer service mode (JUN-98)

A new worker at a counter (a shop, a café, a reception). During training, and only while the worker has turned the mode on, the glasses transcribe the conversation with the DAT Speech capability. On a **Hint** pinch they send the last ~30 seconds; Owl answers with two or three bullets from the company's documents and names the source.

`POST /assist` `{"employee_id": "emp-noa", "transcript": "…", "language": "en"}` (`language` optional: the worker's) →

```json
{
  "bullets": ["Unopened beans: return within 14 days with the receipt", "Refund goes back to the card that paid"],
  "say": null,
  "sources": [{"doc": "Café Kide: counter handbook", "section": "Returns and refunds"}],
  "unsure": false
}
```

- 1–3 bullets, each at most 80 characters, for the display. `say` is always `null`: the glasses do not speak a suggestion while the customer listens.
- `unsure: true` when the documents do not answer it: `bullets` is `["Not in the handbook, ask a colleague"]` (Finnish: "Ei käsikirjassa, kysy työkaverilta") and `sources` is empty. Owl never guesses. With the model, every bullet must rest on a quote found word for word in a document.
- Only the last ~80 words count (`ASSIST_TAIL_WORDS`), so send at most the last half minute; the body may be up to 20 000 characters.
- `404` unknown employee, `409 not_in_training` outside the worker's training period (JUN-96), `403 not_customer_service` when the worker's training plan does not have `customer_service: true`. The glasses offer the mode only when `GET /employees/{id}/training` says `customer_service: true` and `active: true`.
- **The transcript is used for this one answer and dropped**: never written to disk, never logged, never on the stage view, never in an error message.

`GET /assist/sign` → `{"text": "Our trainee wears Owl glasses. Owl listens to suggest answers from our handbook. Nothing is recorded."}`: the sign at the desk. Studio edits it with `PUT /assist/sign` `{"text"}` (≤ 300 characters).

Demo mode or `OWL_MOCK_ASSIST=1`: no model. The local BM25 search looks at the newest sentence first, then two and three sentences, then the last 12, 25 and 80 words, and shows the best sentences of the first section that shares at least two words with it, as they stand in the document. A newest sentence that is a question the documents do not answer gives `unsure`, so an older, answered question never comes back. The scene for the stage: [`docs/runbooks/owl-cafe-script.md`](../runbooks/owl-cafe-script.md). Demo worker: Noa (`emp-noa`, Café Kide, `glasses-6`), on day 2 of 5 of training, with `fixtures/docs/cafe-handbook.md` (opening hours, prices, returns, allergens, loyalty card, payment, Wi-Fi).

### Demo mode (`OWL_DEMO=1`)

`OWL_DEMO_LIVE` lists the parts that still use the live models in demo mode, for the demo on real glasses: `check` (Owl Check: the vision model and the verifier, `decided_by` is `rules` or `jev`), `recognize` (step recognition) and `place` (place recognition). For example `OWL_DEMO_LIVE=check,recognize,place`. Everything else stays scripted.

For the stage demo and the video without models (JUN-69). Only the camera's eyes are scripted: `fixtures/demo-script.json` says what the camera "sees" in each step, by seconds since the step's first frame in a run, and the real engine decides (rules, two frames in a row, the Done pinch, speech). In the pick-and-pack story, step 2 first sees a 0.5 l carton for 1 l (`checking`, then `warning`), then the right box after 12 s; every other step looks done. The story restarts for every `run_id`. Every check answers `decided_by: "demo"`.

Ask answers without a model: the best sentence of the best handbook section, quoted word for word, or "not in our instructions". Record writes the draft from the narration as it is.

### `POST /record/{id}/steps`

Multipart form: `narration` (text, the expert's words for this step; may be empty or left out when nothing was said or heard, and the step is then drafted as "Step N" with no `source` for a person to write in Owl Studio), `photo` (JPEG, one reference frame), `clip` (optional, the step's video as `.mp4` or `.mov`, HEVC or H.264, ≤ 80 MB).

Optional form field `key` (letters, digits and `-`, at most 64): the glasses' own name for this upload, a UUID.

`DELETE /record/{id}/steps/{key}` takes a step upload back. The expert can cancel a slow upload on the glasses, and the glasses then say "Step not saved"; this call makes that true. The step with that `key` is removed with its photo and clip if it has arrived, and an upload with that `key` that arrives later answers `200` and stores nothing. `409` when the recording is already finished. The glasses send it when the expert cancels, and again before the next step or `finish` if it could not be sent then.

Before anything is stored, the server blurs faces in the photo and the clip, and converts the clip for the DAT `VideoPlayer`: H.264 MP4 with faststart, at most 400 px per side and 70 000 pixels (a 720×540 clip becomes 304×228), 15 fps, no audio, the first 10 s. A clip that cannot be read answers `400`.

`POST /record/{id}/finish` answers at once with `status: "processing"`. Poll `GET /record/{id}` every 2 s until `status` is `done` (`process_id` names the new **draft** process; a person reviews and publishes it in Owl Studio) or `failed`. Each recorded step becomes one step: Claude rewrites the narration into a title, an instruction, a spoken sentence and check criteria, and the step keeps the recorded photo and clip. If the model fails, the narration is used as it is, so a recording is never lost: the instruction is then the narration cut at 140 characters (it ends in `…`), and the language is guessed from the words (`fi` or `en`). In both cases the step's `source.quote` holds the **whole** narration, never shortened, so the reviewer reads everything the expert said beside the written step.

The glasses show only processes with `status: "published"`.

### `POST /help/frames`

Multipart form: `image` (JPEG) or `clip` (as in `POST /check`), `employee_id`, `process_id`, `step_id`, `help_id` (empty on the first frame; the answer's `id` is used after that). The first frame opens a session. Send about one frame every 2 s while help is on. `to`: `studio` (the default) or `manager` (JUN-100): with `manager`, the first frame calls the manager on shift instead of the console.

### Help from the shift manager (JUN-100)

The worker calls the manager on shift, who answers on **their own glasses**, sees the worker's live view and talks them through it. Only the manager on shift at the worker's company gets the call.

- `Employee.shift_manager` (bool, default `false`): this person can be on shift and answer on their glasses. The same Owl app shows the manager screens when the assigned employee is a shift manager. Set with `PUT /employees/{id}`; turning it off also takes them off shift.
- `GET /shift` → `{"on_shift": [{"company", "employee_id", "name"}]}`; `PUT /shift` `{"company", "employee_id"}` (Studio; `null` takes the manager off shift; `422` for someone who is not a shift manager).
- `GET /shift/manager?employee_id=<worker>` → `{"employee_id", "name"}`: who the worker's glasses would call; `404` when no one is on shift (Help goes to Studio).

1. **Call:** the worker's glasses send the first Help frame with `to=manager`. The session is `ringing` with `assignee` set. With no one on shift it is `waiting` for Studio with `fallback: "no_manager"`.
2. **Ring:** the manager's glasses poll `GET /help/incoming?employee_id=<manager>` (about every 2 s) → `{"sessions": [HelpSession + "employee_name", "process_title", "step_index", "step_title"]}`: their `ringing` and `accepted` calls, newest first, step names in the manager's language.
3. **Answer:** `POST /help/{id}/accept` `{"employee_id"}` → `accepted`. `POST /help/{id}/later` `{"employee_id"}` → to Studio (`fallback: "later"`). Both `409` when the call is not for that person or no longer rings. After 30 s of ringing (`HELP_RING_SECONDS`) the server moves it to Studio (`fallback: "no_answer"`), checked on every read.
4. **Live view:** the manager's glasses read `GET /help/{id}` about once a second: `latest_frame_url` (a new `?t=` with every frame, so nothing is cached), `frame_at`, `process_id`, `step_id`.
5. **Talk:** `POST /help/{id}/say` with `from: "manager"` (spoken and shown on the worker's glasses) and `from: "worker"` (shown to the manager). A mark is only for the Studio expert.
6. **End:** either side calls `POST /help/{id}/end`. The frames are deleted, as for any Help session.

Demo mode: Mika (`emp-mika`, `glasses-7`, Kide Logistics) is the manager on shift unless Studio set someone. Sami calls him from one simulator, Mika answers in the other.

### `POST /help/{id}/say`

```json
{"from": "expert", "text": "The blue carton, top shelf.", "mark": {"x": 0.42, "y": 0.31}}
```

`from` defaults to `expert`. `mark` is optional: the point the expert clicked in the worker's view, as a share of the frame's width and height from its top left corner (0–1). The server draws a ring there on a copy of the latest frame and puts it in the message's `image_url`. A mark from the worker, or one sent when there is no frame, is ignored and the text still arrives. `409` when the session has ended.

## Languages

- `GET /processes?language=fi` and `GET /processes/{id}?language=fi` answer in that language when a translation of the process is stored, and with the original otherwise. `fi-FI` finds the `fi` translation.
- A translation is the same process: same `id`, step ids, media, check kinds, SKUs and quantities. Only the words differ, and its `status` follows the original.
- Translations come from `fixtures/process-<name>.<lang>.json` and from `PUT /processes/{id}?language=<lang>`. They are never listed as processes of their own.
- `/check` and `/ask` take the language from the request or the employee, as before.

## Media

- The API returns **absolute** URLs. It builds them from `PUBLIC_BASE_URL` when that is set (the https tunnel), otherwise from the request's own address. The fixtures store paths (`/media/...`); the API turns them into URLs.
- The DAT `VideoPlayer` plays `https` URLs only, so clips need the tunnel. Images can also be downloaded by the phone app and drawn with `Image(image: UIImage)`.
- Check frames are not stored. Faces in recorded photos and clips are blurred before they are stored (JUN-32).
- Help frames are kept only while the session is open. `/media` needs no token, so each session's frames live in a folder with a random name that cannot be guessed. Ending the session deletes the folder and the URLs stop working. Frames left behind by an earlier run are deleted when the server starts.
