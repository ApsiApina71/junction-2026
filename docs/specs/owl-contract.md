# Owl contract: data model and API

The shared JSON shapes and endpoints of `apps/owl-api`. The glasses app (`apps/owl-glasses`) and Owl Studio build against this, first on the mock data in [`apps/owl-api/fixtures/`](../../apps/owl-api/fixtures/), then on the real engine. Same shapes in both.

- **Ticket:** [JUN-27](https://linear.app/junction-2026-bossit/issue/JUN-27). The API is [JUN-28](https://linear.app/junction-2026-bossit/issue/JUN-28).
- **Spec:** [Onboarding Owl](onboarding-owl.md)
- **Owner:** the owl-api session. Ask for changes; do not edit this file from another app's work.

## Basics

- Base URL `http://<mac ip>:8000` on the venue network, plus an `https://` tunnel URL for video (see [Media](#media)).
- JSON, UTF-8, `snake_case` keys. Missing optional fields are `null`, never left out.
- **Auth:** when the server sets `API_TOKEN`, every endpoint except `/health` and `/media/*` needs the header `X-Api-Token: <token>`. Without it the API answers `401`.
- **Errors:** `{"detail": "<one sentence for a human>"}` with the status code:

| Code | When | What the glasses app does |
|---|---|---|
| 400 / 415 / 413 | Bad upload (not an image, wrong type, too big) | Bug; log it |
| 401 | Wrong or missing token | "Ask your supervisor" screen |
| 404 | Unknown process, step, help or record id | Reload the process list |
| 422 | Missing or invalid field | Bug; log it |
| 429 | Model rate limited | Retry after 2 s |
| 500, 502, 503, no answer | Server bug, model or network error | "Owl can't see right now" and keep going without the check. A step finished this way is **not checked**: never show it as verified (JUN-57) |

- **Languages** are BCP 47 tags (`en`, `fi`, `uk`, `ar`). `say` and `text` fields come in the employee's language. See [Languages](#languages).

## Display limits (from the DAT docs)

Meta Ray-Ban Display renders at **600×600**. Owl keeps text short so a step fits on one screen.

| Field | Limit |
|---|---|
| `Step.title` | ≤ 32 characters |
| `Step.instruction`, `CheckResult.text`, `Answer.text` | ≤ 140 characters |
| Every `say` | ≤ 25 words, no markdown or emoji |
| Images (`*_image_url`) | JPEG, longest side ≤ 600 px |
| Clips (`clip_url`) | MP4 (H.264), ≤ 400 px per side and ≤ 70 000 pixels in total (for example 352×198 or 264×264), `https` only, one at a time |

## Shapes

### Employee

```json
{
  "id": "emp-sami",
  "name": "Sami",
  "language": "en",
  "role": "Warehouse picker",
  "company": "Kide Logistics",
  "welcome": "Welcome to Kide, Sami! Today you learn to pick and pack an order. I'm Owl. I'll show you each step.",
  "process_ids": ["proc-pick-pack"],
  "glasses_id": "glasses-1"
}
```

- `company`: the company of the worker's first task; without a task, the company this owl-api runs for (`OWL_COMPANY`, by default the demo worker's). One company per server: multi-company admin is out of scope.
- `welcome` is the personal welcome shown and spoken on the first start (JUN-41). Owl writes it from the name, the company and the first task, in the employee's language, and rewrites it when one of those changes. A welcome written by hand in Owl Studio stays as written.
- `glasses_id` is the pair of glasses the employee wears, or `null`. The employer names the pairs (`glasses-1`; letters, digits, `-` and `_`). A pair has one worker at a time: assigning it to someone takes it from whoever had it.

### Process

```json
{
  "id": "proc-pick-pack",
  "title": "Pick and pack an order",
  "summary": "Take a box, pick the items on the order, check them, pack and seal.",
  "company": "Kide Logistics",
  "language": "en",
  "status": "published",
  "source": "record",
  "expert": "Laura",
  "steps": [Step, ...]
}
```

- `status`: `draft` (just recorded, only in Owl Studio) or `published` (shown on the glasses).
- `source`: `record` (an expert recorded it) or `docs` (written from the documents).

### Step

```json
{
  "id": "step-2",
  "index": 2,
  "title": "Pick the items",
  "instruction": "Pick every item on the order from the shelf into the box.",
  "say": "Pick the three items on the order into the box.",
  "reference_image_url": "https://owl.example/media/proc-pick-pack/step-2.jpg",
  "clip_url": "https://owl.example/media/proc-pick-pack/step-2.mp4",
  "check": {
    "kind": "order",
    "criteria": ["Every order line is in the box", "No extra items"],
    "order_lines": [{"sku": "OAT-1L", "name": "Oat drink 1 l", "qty": 2}]
  },
  "source": {"doc": "Laura's recording", "quote": "Always check the litre size, the 0.5 l and 1 l cartons look the same."},
  "reviewed": true
}
```

- `index` starts at 1.
- `say` is what the glasses speak when the step opens. `instruction` is the text on the display.
- `reference_image_url`: the expert's photo of the finished step, or `null`.
- `clip_url`: a 5–10 s clip of the expert doing the step ("Watch how"), or `null`.
- `check.kind`:
  - `visual`: the camera view is checked against each of the `criteria`. The reference image is shown to the vision model as context and on the display, but it never decides on its own: a step passes only when every criterion was seen and met. A visual step without criteria can never pass.
  - `order`: the products and quantities seen are compared with `order_lines`.
  - `none`: no check. The worker confirms the step with a pinch.
- `check.order_lines` is set only for `order` checks.
- `source` is where the step comes from, or `null`. For a recorded step its `quote` is the expert's whole narration.
- `reviewed` (default `true`): `false` on a step that Owl wrote from a recording and that no person has checked yet. Owl Studio sets it to `true` when the reviewer has read the step against the narration. `PUT /processes/{id}` answers `422` when the body is `published` and a step is not reviewed; saving a draft is always allowed.

### CheckResult

Answer to one camera frame during a step.

```json
{
  "status": "warning",
  "problem": "wrong_item",
  "text": "Wrong size: 0.5 l. The order says 1 l.",
  "say": "Wrong item: 0.5 l, the order says 1 l.",
  "hint": null,
  "lines": [
    {"name": "Oat drink 1 l", "expected": 2, "seen": 1, "status": "wrong_item", "note": "1 × Oat drink 0.5 l"},
    {"name": "Coffee 500 g", "expected": 1, "seen": 1, "status": "ok", "note": null},
    {"name": "Rye crispbread", "expected": 1, "seen": 1, "status": "ok", "note": null}
  ],
  "confidence": 0.91,
  "decided_by": "jev",
  "step_done": false
}
```

- `status`:
  - `ok`: the step looks right. If the request had `final: true`, `step_done` is `true`.
  - `warning`: a problem was seen in two frames in a row. Show `text` and speak `say`. `say` is set only on the frame where the warning is confirmed or changes, and on every Done pinch; while the same problem stays, later frames repeat `text` with `say: null`.
  - `checking`: a problem was seen once and waits for the next frame. `say` is `null`, so stay quiet.
  - `unsure`: Owl cannot tell (blurry, too far, hand in the way). `hint` says what to do ("Move closer to the box"). Speak it only on a final check.
- `problem`: `wrong_item | missing | too_many | not_matching | null`. `not_matching` is for visual steps.
- `lines`: one row per order line for `order` checks. `null` for `visual` and `none`.
  - `lines[].status`: `ok | wrong_item | missing | too_many`.
  - `lines[].note`: what was seen instead, or `null`.
- `confidence`: Jev's reported probability for its answer (0–1), or `null` when the rules decided alone. It is not a calibrated chance that the step is right: **never show it as a percentage**.
- `decided_by`: `jev` (Jev agreed with the rules above the server's threshold), `rules` (the deterministic compare decided alone, for example without a Jev key) or `demo` (demo mode: the camera observation is scripted, see below).
- `step_done`: `true` only when `final` was sent and the step is right. **A step is never done while something is wrong.**

**What a passed check means.** Vision describes one frame; the rules decide from that description. A product vision did not map to an order line counts as something extra in the box, and a criterion that was not answered is not passed (`unsure`). Jev, when on, is a second opinion on the decision from the same description: it cannot catch an item vision missed or misread. The "two frames in a row" rule is consistency over time from the same model, not an independent confirmation. So a passed check covers only what was visible in the frame and reviewed against the step, and the apps say no more than that ("Owl checked the box", not "the order is correct").

### Answer

```json
{
  "found": true,
  "text": "Mark the line as missing on the order and tell the shift lead. Never swap in another product.",
  "say": "Mark it missing and tell the shift lead. Don't swap in another product.",
  "language": "en",
  "sources": [{"doc": "Warehouse handbook", "section": "Out of stock", "quote": "If an item is out of stock, mark the line as missing and tell the shift lead."}]
}
```

`found: false` means the answer is not in the company's instructions. `text` then says so ("That's not in our instructions. Ask your shift lead."), and `sources` is `[]`.

### Doc

```json
{"id": "doc-handbook", "title": "Warehouse handbook", "filename": "warehouse-handbook.md", "chars": 2400, "uploaded_at": "2026-11-14T09:00:00+02:00"}
```

### HelpSession

```json
{
  "id": "help-1",
  "status": "waiting",
  "employee_id": "emp-sami",
  "process_id": "proc-pick-pack",
  "step_id": "step-2",
  "latest_frame_url": "https://owl.example/media/help/help-1-Zk3vTq8mXw2LrN5d/latest.jpg?t=9f2c1a7b",
  "frame_at": "2026-11-14T10:12:18+02:00",
  "updated_at": "2026-11-14T10:12:20+02:00",
  "messages": [
    {"id": 1, "from": "worker", "text": "Which oat drink is it?", "at": "2026-11-14T10:12:00+02:00", "image_url": null},
    {"id": 2, "from": "expert", "text": "The blue carton, top shelf.", "at": "2026-11-14T10:12:20+02:00", "image_url": "https://owl.example/media/help/help-1-Zk3vTq8mXw2LrN5d/mark-2.jpg"}
  ]
}
```

- `status`: `waiting` (no expert yet), `connected` (an expert has answered), `ended`.
- The glasses speak every `expert` message once. `id` grows, so the app remembers the last one it spoke.
- `frame_at`: when the latest frame arrived. `updated_at` also moves when someone speaks, so the console uses `frame_at` to tell a live view from a stale one.
- `messages[].image_url`: the worker's own view with a ring where the expert pointed, or `null`. The glasses show it with the expert's words.
- When the session ends, its frames are deleted, and `latest_frame_url` and every `image_url` become `null`.

### Recording

```json
{
  "id": "rec-1",
  "title": "Pick and pack an order",
  "expert": "Laura",
  "status": "recording",
  "steps": [
    {"index": 1, "narration": "First take a medium box...", "photo_url": "https://.../rec-1/1.jpg", "clip_url": "https://.../rec-1/1.mp4"}
  ],
  "process_id": null
}
```

- `status`: `recording`, `processing` (the AI is writing the steps), `done` (`process_id` is set), `failed`.

| Method and path | Body | Answer | Used by |
|---|---|---|---|

| `GET /employees` | none | `{"employees": [Employee]}` | Studio |
| `POST /employees` | JSON (below) | `Employee` | Studio |
| `GET /employees/{id}` | none | `Employee` | glasses, Studio |
| `PUT /employees/{id}` | JSON, any of the `POST /employees` fields | `Employee` | Studio |
| `GET /employees/{id}/progress` | none | `Progress` (below) | glasses only |
| `GET /stats` | none | anonymous totals (below) | Studio, pitch |
| `GET /glasses/{glasses_id}/employee` | none | `Employee`, or `404` when the pair is not assigned | glasses |
| `GET /processes` | none; optional `?language=fi` | `{"processes": [Process]}` (published and drafts, steps included) | glasses, Studio |
| `GET /processes/{id}` | none; optional `?language=fi` | `Process` | glasses, Studio |
| `PUT /processes/{id}` | `Process` | `Process` (edit, reorder, publish or translate; below) | Studio |
| `POST /check` | multipart (below) | `CheckResult` | glasses |
| `POST /ask` | JSON (below) | `Answer` | glasses |
| `GET /docs` | none | `{"docs": [Doc]}` | Studio |
| `POST /docs` | multipart `file` (`.md`, `.txt`, `.pdf`, ≤ 10 MB) | `Doc` | Studio |
| `DELETE /docs/{id}` | none | `204`, no body | Studio |
| `POST /record` | JSON `{"title", "expert"}` | `Recording` | glasses |
| `POST /record/{id}/steps` | multipart (below) | `Recording` | glasses |
| `POST /record/{id}/finish` | none | `Recording` (`processing`, then `done`) | glasses |
| `GET /record` | none | `{"recordings": [Recording]}` (newest first) | Studio |
| `GET /record/{id}` | none | `Recording` | glasses, Studio |
| `POST /help/frames` | multipart (below) | `HelpSession` | glasses |
| `GET /help` | none | `{"sessions": [HelpSession]}` (open ones first) | Studio |
| `GET /help/{id}` | none | `HelpSession` | glasses (poll every 2 s), Studio |
| `POST /help/{id}/say` | JSON `{"from": "expert" \| "worker", "text", "mark"}` (below) | `HelpSession` | Studio, glasses |
| `POST /help/{id}/end` | none | `HelpSession` | glasses, Studio |
| `GET /media/{path}` | none | JPEG or MP4 | glasses display, Studio |

The record and help endpoints add to the list fixed in JUN-27. Each recorded step is uploaded on its own, so a long recording never sends one huge request. The employee list, the glasses, `DELETE /docs/{id}`, `?language=` and `mark` come from Owl Studio and Help (JUN-33, JUN-38, JUN-41, JUN-60).

### `POST /employees` and `PUT /employees/{id}`

```json
{"name": "Aino", "language": "fi", "role": "Packer", "process_ids": ["proc-pick-pack"], "glasses_id": "glasses-1", "welcome": null}
```

- `POST` needs `name` (1–60 characters) and `language`. `role` defaults to `""`, `process_ids` to `[]`, `glasses_id` to `null`.
- The server makes the `id` from the name (`emp-aino`, then `emp-aino-2`) and takes `company` from the employees and processes it already has.
- `welcome` empty or `null`: Owl writes it. English and Finnish have their own wording; other languages get the English one until someone writes theirs by hand.
- `PUT` changes only the fields that are sent. `"glasses_id": null` takes the glasses away, and `"welcome": ""` hands the welcome back to Owl.
- An unknown id in `process_ids` is a `422`. `PUT` on an unknown employee is a `404`.

### `GET /glasses/{glasses_id}/employee`

The glasses app asks this on "Hey Meta, start Owl" to learn who wears this pair. `404` with `{"detail": "These glasses are not assigned to anyone yet."}` when no one does.

### `PUT /processes/{id}`

- The server numbers `Step.index` 1, 2, 3… from the order of `steps` and keeps every step `id`, so Owl Studio reorders and deletes steps by sending the array as it should be. Two steps with the same `id` are a `422`.
- Without `?language=` the body replaces the process itself. Its `language` can be corrected this way too (a recording's language is a guess). When its words or its language change (titles, instructions, `say`, checks, sources, the steps or their order), stored translations are dropped, because they would say what the process used to say. Publishing alone keeps them.
- With `?language=sv` the body is stored as that language's translation, and the original does not change. It must keep the original's step ids in the same order (`422` otherwise). Its `status` is ignored: publishing happens on the original.

### `DELETE /docs/{id}`

Ask stops using the document at once and the uploaded file is deleted. `404` for an unknown id. The handbook that ships in `fixtures/docs/` is only forgotten until the server restarts.

### `POST /check`

Multipart form:

| Field | Type | Notes |
|---|---|---|
| `image` | file, `image/jpeg` or `image/png`, ≤ 6 MB | A camera **stream** frame, not a photo capture: Meta's known issue says capture holds back display updates on Display glasses. |
| `clip` | file, `video/mp4` or `.mov`, ≤ 18 MB | **Instead of `image`**, when the phone cannot decode the stream itself: about 1 s of the hvc1 (or H.264) stream, starting at a key frame. The server uses its last frame. Send exactly one of `image` and `clip` (both or neither: `422`; an unreadable clip: `400`). |
| `process_id` | text | |
| `step_id` | text | |
| `run_id` | text | A UUID the glasses app makes when the worker starts a process. The "two frames in a row" rule is kept per run and step. |
| `final` | text `true` / `false`, default `false` | `true` on the "Done" pinch. |
| `language` | text, optional | Defaults to the employee's language. |
| `employee_id` | text, optional | The worker, for their own learning progress (JUN-73). |

Why `clip`: with the phone locked in a pocket the app runs in the background, and the DAT `raw` video codec stops delivering frames there; `hvc1` keeps delivering compressed frames ([VideoCodec](https://wearables.developer.meta.com/docs/reference/ios_swift/dat/1.0/mwdatcamera_videocodec)). The phone decodes them when it can and falls back to `clip` when iOS refuses background decoding.

Send one frame at a time and wait for the answer, about one frame every 1–2 s during an order step. While the server is busy with the same run, it answers `{"status": "checking", ...}` at once.

### `POST /ask`

```json
{"question": "What if an item is out of stock?", "employee_id": "emp-sami", "process_id": "proc-pick-pack", "step_id": "step-2", "language": "en"}
```

Only `question` is required. The question is the final transcription from the glasses' Speech capability.

When all documents together are larger than `ASK_MAX_CHARS`, only the best sections for the question go to the model, picked by a local BM25 index on this server (JUN-71). Source quotes are still checked against the whole documents.

### Learning progress (JUN-73)

Owl is a learning aid, not monitoring: the EU AI Act treats AI that monitors workers as high-risk. So the worker sees their own progress on their glasses, and the company sees only anonymous totals. **Owl Studio never shows one person's results.**

`GET /employees/{id}/progress` (the worker's own glasses only):

```json
{
  "employee_id": "emp-sami",
  "tasks_done": 2,
  "steps_done": 10,
  "problems_caught": 1,
  "problems_fixed": 1,
  "runs": [{"run_id": "…", "process_id": "proc-pick-pack", "title": "Pick and pack an order", "started_at": "…", "finished_at": "…", "seconds": 240, "steps_done": 5, "problems_caught": 0, "problems_fixed": 0}],
  "faster_than_first": true
}
```

- A run starts with its first `/check` and is finished when the process's last step is done. `runs` is newest first.
- `problems_caught` counts each spoken warning once; `problems_fixed` counts a warned step that then came out ok.
- `faster_than_first`: the latest finished run of a task against the first finished run of the same task, or `null` when there is only one.

`GET /stats` (no names, no ids): `{"runs", "tasks_finished", "workers", "median_seconds_to_first_finished_task", "problems_caught", "problems_fixed"}`. Runs live in memory and reset when owl-api restarts.

### Demo mode (`OWL_DEMO=1`)

For the stage demo and the video without models (JUN-69). Only the camera's eyes are scripted: `fixtures/demo-script.json` says what the camera "sees" in each step, by seconds since the step's first frame in a run, and the real engine decides (rules, two frames in a row, the Done pinch, speech). In the pick-and-pack story, step 2 first sees a 0.5 l carton for 1 l (`checking`, then `warning`), then the right box after 12 s; every other step looks done. The story restarts for every `run_id`. Every check answers `decided_by: "demo"`.

Ask answers without a model: the best sentence of the best handbook section, quoted word for word, or "not in our instructions". Record writes the draft from the narration as it is.

### `POST /record/{id}/steps`

Multipart form: `narration` (text, the expert's words for this step), `photo` (JPEG, one reference frame), `clip` (optional, the step's video as `.mp4` or `.mov`, HEVC or H.264, ≤ 80 MB).

Before anything is stored, the server blurs faces in the photo and the clip, and converts the clip for the DAT `VideoPlayer`: H.264 MP4 with faststart, at most 400 px per side and 70 000 pixels (a 720×540 clip becomes 304×228), 15 fps, no audio, the first 10 s. A clip that cannot be read answers `400`.

`POST /record/{id}/finish` answers at once with `status: "processing"`. Poll `GET /record/{id}` every 2 s until `status` is `done` (`process_id` names the new **draft** process; a person reviews and publishes it in Owl Studio) or `failed`. Each recorded step becomes one step: Claude rewrites the narration into a title, an instruction, a spoken sentence and check criteria, and the step keeps the recorded photo and clip. If the model fails, the narration is used as it is, so a recording is never lost: the instruction is then the narration cut at 140 characters (it ends in `…`), and the language is guessed from the words (`fi` or `en`). In both cases the step's `source.quote` holds the **whole** narration, never shortened, so the reviewer reads everything the expert said beside the written step.

The glasses show only processes with `status: "published"`.

### `POST /help/frames`

Multipart form: `image` (JPEG) or `clip` (as in `POST /check`), `employee_id`, `process_id`, `step_id`, `help_id` (empty on the first frame; the answer's `id` is used after that). The first frame opens a session. Send about one frame every 2 s while help is on.

### `POST /help/{id}/say`

```json
{"from": "expert", "text": "The blue carton, top shelf.", "mark": {"x": 0.42, "y": 0.31}}
```

`from` defaults to `expert`. `mark` is optional: the point the expert clicked in the worker's view, as a share of the frame's width and height from its top left corner (0–1). The server draws a ring there on a copy of the latest frame and puts it in the message's `image_url`. A mark from the worker, or one sent when there is no frame, is ignored and the text still arrives. `409` when the session has ended.

## Languages

- `GET /processes?language=fi` and `GET /processes/{id}?language=fi` answer in that language when a translation of the process is stored, and with the original otherwise. `fi-FI` finds the `fi` translation.
- A translation is the same process: same `id`, step ids, media, check kinds, SKUs and quantities. Only the words differ, and its `status` follows the original.
- Translations come from `fixtures/process-<name>.<lang>.json` and from `PUT /processes/{id}?language=<lang>`. They are never listed as processes of their own.
- `/check` and `/ask` take the language from the request or the employee, as before.

## Media

- The API returns **absolute** URLs. It builds them from `PUBLIC_BASE_URL` when that is set (the https tunnel), otherwise from the request's own address. The fixtures store paths (`/media/...`); the API turns them into URLs.
- The DAT `VideoPlayer` plays `https` URLs only, so clips need the tunnel. Images can also be downloaded by the phone app and drawn with `Image(image: UIImage)`.
- Check frames are not stored. Faces in recorded photos and clips are blurred before they are stored (JUN-32).
- Help frames are kept only while the session is open. `/media` needs no token, so each session's frames live in a folder with a random name that cannot be guessed. Ending the session deletes the folder and the URLs stop working. Frames left behind by an earlier run are deleted when the server starts.
